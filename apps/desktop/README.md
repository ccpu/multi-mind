# @app/desktop

The Tauri application: a React frontend in `src/` and the Rust backend in
`src-tauri/`. Run everything from the repository root.

```sh
pnpm dev      # the desktop app (Vite + the Rust backend)
pnpm dev:web  # the frontend alone in a browser, no Rust toolchain needed
pnpm bundle   # installers for the current platform, into src-tauri/target/release/bundle
```

## Layout

```
apps/desktop
├── index.html              # Vite entry document
├── vite.config.ts          # one line: the shared Tauri-aware config
├── src/                    # React frontend
│   ├── main.tsx            # mounts <App>, imports the Tailwind globals
│   ├── App.tsx
│   └── components/         # window-specific components
├── test/                   # frontend tests (jsdom, the Rust bridge mocked)
└── src-tauri/              # Rust backend
    ├── Cargo.toml
    ├── tauri.conf.json     # windows, bundle, CSP, the before* commands
    ├── build.rs
    ├── capabilities/       # what each window is allowed to do
    ├── icons/              # generated by `pnpm gen:icons`
    └── src/
        ├── main.rs         # two-line shim
        ├── lib.rs          # builder: plugins, commands, setup
        └── commands.rs     # the #[tauri::command] functions
```

There is no preload script and no renderer process to configure. A Tauri
frontend is an ordinary web app with no access to the system; everything it can
do is a command the Rust side registered or a plugin permission the window was
granted.

## Adding a command

1. Write it in `src-tauri/src/commands.rs`:

   ```rust
   #[tauri::command]
   pub fn word_count(text: &str) -> usize {
       text.split_whitespace().count()
   }
   ```

2. Register it in the `generate_handler!` list in `src-tauri/src/lib.rs`. A
   command that is not in that list does not exist as far as the frontend is
   concerned.
3. Add the typed wrapper in `packages/tauri-api` so the frontend never touches
   `invoke` directly.

Long-running work should be `async fn` — Tauri runs async commands off the main
thread, so the window keeps painting.

## Adding a plugin

```sh
pnpm --filter @app/desktop exec cargo add tauri-plugin-dialog
pnpm --filter @app/desktop add @tauri-apps/plugin-dialog
```

Then register it in `lib.rs` (`.plugin(tauri_plugin_dialog::init())`) and add its
permission to `src-tauri/capabilities/default.json`. The permission is not
optional: without it the call fails at runtime even though it compiles.

## Adding a window

Add another entry to `app.windows` in `tauri.conf.json` with its own `label` and
`url` (`index.html`, `settings.html`, …), add the extra HTML entry point to the
Vite config's `build.rollupOptions.input`, and give the new label a capability
file — or add the label to the existing one. Windows created at runtime instead
use `WebviewWindowBuilder` in Rust or `WebviewWindow` from `@tauri-apps/api`.

## Content Security Policy

`tauri.conf.json` sets a restrictive `csp` for release builds and a looser
`devCsp` for `tauri dev`, where Vite needs inline scripts for hot reload. Tauri
adds hashes for the inline scripts in the bundled frontend, so the production
policy does not need `unsafe-inline`. If a dev-only resource is blocked, widen
`devCsp` rather than `csp`.

## Versions

Three files carry the version: `package.json`, `src-tauri/Cargo.toml` and
`src-tauri/tauri.conf.json`. `tauri.conf.json` is the one that names the
installers. The release workflow reads the git tag, so keep them in step when
you bump.
